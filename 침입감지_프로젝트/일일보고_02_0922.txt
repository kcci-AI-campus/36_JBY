[3] 오늘 진행 업무
- 학습 입력 크기 비교 실험 : 동일 데이터(train 621 / test 189)로 640과 320을 각각
  60 epoch 학습 후 둘 다 보드 조건인 320으로 평가.
  640 학습이 mAP50-95 0.8592로 320 학습(0.8537)보다 우세하여 640을 채택
- LiteRT 변환 3종 및 정확도 비교
  float32 0.8351 / INT8 0.7797 / w8a32 0.8413 (mAP50-95, 입력 320)
  → INT8만 6.6% 하락, w8a32는 손실 없음을 확인
- 보드 성능 자동 측정 도구 작성(bench_models.py) : 모델별로 카메라·전처리·추론·
  후처리 시간을 나누어 재고 FPS·CPU·온도를 표와 CSV로 저장
- 보드 실측 : 세 모델 모두 20.0 FPS로 동일. 추론은 INT8 8.85ms, FP32 24.72ms로
  2.8배 차이가 나는데 FPS가 같아 카메라가 병목임을 확인
- 카메라를 제외한 순수 추론 한계 측정 : INT8 115.9 FPS, FP32 39.4 FPS
  → 현재 카메라 20 FPS는 INT8 능력의 17%만 사용하는 상태
- 추론 스레드 수 비교(1/2/4) : CPU 사용률 10.1% / 13.3% / 17.7%
  1스레드로 CPU 43% 절감 가능하나 프레임 누락 발생
- 파이프라인 트레이싱 연결(--trace) : 단계별 시간과 코어별 CPU를 기록해
  Perfetto 타임라인으로 확인 가능하도록 구성
- 보호자 휴대폰 알림 기능 구현 및 동작 확인 : 경보 발생 시 해당 시점 화면을
  사진으로 전송. 전송은 별도 스레드에서 처리해 추론이 멈추지 않도록 함
- 경보 전후 영상 전송 기능 구현 : 최근 3초를 메모리에 유지하다가 경보 시
  앞 3초 + 뒤 2초를 동영상으로 묶어 전송(접근 과정이 남도록)
- 웹 실시간 화면 구현(--web) : 브라우저에서 영상·상태·FPS·온도 확인 가능
- 팀 통합 대시보드 구성 : 보드 4대를 한 화면에 표시. 꺼진 보드는 '연결 없음'으로
  표시되고 위험 상태인 보드는 테두리가 강조되도록 구성
- LED 배선 시험 도구 작성(led_test.py) : 배선 확인을 추론 코드와 분리

[4] 문제점 및 검토 필요 사항
- 기울어진 칼의 인식률이 낮음. 학습 데이터가 정면·수평 위주로 구성되어 있어
  기울기 각도를 달리한 데이터를 추가 촬영할 예정
- 자체 학습한 INT8 모델이 실제 웹캠 환경에서 칼을 검출하지 못함.
  Colab 평가에서는 mAP50 0.980이었으나 실사용과 차이가 큼.
  원인이 양자화인지 학습 데이터인지 미확인이며, 동일 장면으로 모델별 검출률을
  비교하는 도구(detect_rate.py)를 작성해 두었으나 측정은 미완
  → 임시로 팀원 모델(float32)을 사용 중이며, 이 경우 CPU가 50%로
     INT8(17.7%) 대비 3배 소모되어 저전력 목표가 약화됨
- 카메라 20 FPS 병목. v4l2-ctl 조회 결과 이 웹캠은 MJPG 640x480에서
  30 fps를 지원한다고 보고하므로 하드웨어 한계는 아님.
  프레임 간격이 36~64ms로 불규칙한 점으로 보아 자동 노출이 원인으로 추정되며,
  노출 고정 조건 측정이 미완이라 확정하지 못함
- 스레드 수에 따른 FPS 측정값이 신뢰할 수 없음. 2스레드(16.3)가 1스레드(17.4)보다
  낮게 나왔는데, 위 카메라 간격 불규칙이 원인으로 판단됨.
  카메라 문제 해결 후 재측정 필요. 현재는 CPU 절감분만 유효한 수치임
- 휴대폰 알림 방식으로 블루투스가 제안되었으나, 통신 거리가 약 10m로 제한되어
  보호자가 외출한 상황에서 동작하지 않음. 인터넷 푸시 방식으로 구현하여
  거리 제한 없이 수신되는 것을 확인함
- 팀 대시보드에서 다른 보드의 상태 값을 읽으려면 각 보드가 교차 출처 접근을
  허용해야 함. 영상은 제한 없이 표시되나 상태 텍스트가 표시되지 않아
  팀원 코드에 한 줄 추가 요청 예정
