 detect_baby.py   ← 많이 바뀌었습니다. 반드시 교체
   · 경보가 울린 뒤 프로그램이 죽던 버그 세 개를 고쳤습니다.

 1. 기본 실행
────────────────────────────────────────────────────────────

    cd ~/work/baby
    python3 detect_baby.py v2e120_fp32_640.tflite --web

  자주 쓰는 옵션
    --web          브라우저로 실시간 보기 (포트 5000)
    --notify       위험하면 휴대폰으로 알림 (notify.json 필요)
    --clip         경보 전후 5초 영상을 휴대폰으로
    --no-gui       화면 없이 (SSH 만으로 돌릴 때)
    --seconds 30   30초 뒤 자동 종료하고 측정값을 찍는다
    --team         팀 보드 4대를 한 화면에

  ※ notify.json 은 안 들어 있습니다. 텔레그램/ntfy 토큰이 비밀번호와
    같아서 공유본과 GitHub 에서 뺐습니다. 필요하면 따로 말씀 주세요.

 2. 중요 — 모델은 v2e120 을 쓰세요 (v2f 아님)
────────────────────────────────────────────────────────────

  detect_rate.py 로 같은 60프레임을 15개 모델에 똑같이 먹여 비교했습니다.
  (모델마다 다시 찍으면 칼 각도가 달라져 비교가 안 됩니다)

    모델                학습            knife@0.25   knife@0.40  신뢰도
    ------------------------------------------------------------------
    v2e120_fp32_640    에폭 120          100 %        100 %      0.68
    v2f_fp32_640       에폭 80, final     25 %          0 %      0.28
    v2f_int8_640       위와 같은 가중치      0 %          0 %       -
    320 입력 전부(5종)   -                  0 %          0 %       -

  ① 최종 데이터셋으로 새로 학습한 v2f 가 오히려 4배 나쁩니다.
     "최신이 최선" 이 아니었습니다. mAP 만 보고 골랐으면 칼을 25%
     밖에 못 찾는 걸 제출할 뻔했습니다.
  ② 320 입력은 다섯 종 전부 knife 0% 입니다. 입력 640 이 아니면
     1.5~2m 거리의 커터칼은 아예 못 찾습니다(픽셀이 21개뿐).
  ③ INT8 이 0% 인 건 양자화 탓이 아닙니다. 원본 FP32 가 이미 25%
     였습니다. 그래서 v2e120 으로 INT8 을 다시 만드는 중입니다.

  >> 팀원B님께 부탁 <<
     ptfile.zip 의 가중치(에폭 60~120)가 **어떤 데이터셋**으로 학습된
     것인지 알려 주세요. v2e120 과 v2f 는 에폭(120 vs 80)과 데이터셋이
     동시에 다릅니다. 변수가 둘이라 "데이터를 늘린 게 해로웠다"고
     단정할 수 없습니다. 같은 데이터로 120에폭까지 돌려 보면
     단순히 덜 학습된 것인지 바로 갈립니다.

  파일 이름 규칙 (겹쳐서 덮어쓴 사고가 한 번 있었습니다)
     by_*     우리(정보윤) 학습, merged_v3
     v2_*     팀원B님 이전 학습
     v2f_*    팀원B님 merged_dataset_final 80에폭
     v2e120_* 팀원B님 ptfile.zip 의 에폭 120     ← 지금 제일 좋음
     ** best.tflite 같은 이름으로 주고받지 맙시다. 덮어써집니다. **

 3. 새 기능 — 집 밖(LTE)에서 실시간 영상 보기
────────────────────────────────────────────────────────────

  --web 이 주는 주소(http://10.10.15.xx:5000)는 같은 와이파이에서만
  열립니다. 공유기가 바깥에서 들어오는 연결을 막기 때문입니다(NAT).
  포트포워딩으로 뚫을 수 있지만 교육장 공유기는 권한이 없습니다.

  cloudflared 를 쓰면 보드가 밖으로 먼저 연결을 걸어 그 통로로
  외부 접속을 받습니다. 가입도 요금도 없습니다.

  설치 (한 번만)
    curl -L https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-arm64 -o cloudflared
    chmod +x cloudflared
    sudo mv cloudflared /usr/local/bin/

  실행 — 터미널 두 개가 필요합니다
    [터미널 1] 켜 두고 그대로 둡니다. 끄면 주소가 죽습니다.
        cloudflared tunnel --url http://localhost:5000

    [터미널 2] auto 를 주면 주소를 자동으로 받아옵니다.
        python3 detect_baby.py v2e120_fp32_640.tflite --web --notify --web-url auto

    시작할 때 이 줄이 나오면 성공입니다.
        [알림] cloudflared 에서 주소를 받아왔습니다 : https://....trycloudflare.com

  MobaXterm 은 왼쪽 세션을 더블클릭하면 탭이 하나 더 열립니다.

  자주 겪는 것
    Error 1033  → cloudflared 가 안 돌고 있습니다. 다시 켜고 새 주소를 쓰세요
    502         → 터널은 살아 있는데 detect_baby.py 가 꺼져 있습니다
    알림을 눌렀는데 10.10.15.61 로 감
                → 그 알림이 옛 실행에서 온 것입니다. 새 알림을 누르세요

  ※ 주의 : 터널 주소는 비밀번호와 같습니다. 아는 사람은 누구나 우리
    카메라를 봅니다. 인증이 없습니다. ntfy 토픽 이름도 마찬가지입니다.
    ** 발표 자료 캡처에서 주소창과 토픽 이름을 가려 주세요. **
    그리고 껐다 켤 때마다 주소가 바뀝니다. 발표 직전에 켜세요.


────────────────────────────────────────────────────────────
 4. 성능 측정 — 실사용 기준으로만
────────────────────────────────────────────────────────────

  보고서에 쓸 숫자는 실제 프로그램을 돌려서 나온 값만 씁니다.
  bench_models.py 의 수치는 참고용이고 보고서에 쓰지 마세요
  (카메라 없이 재서 실제보다 빠르게 나옵니다).

      python3 detect_baby.py <모델> --web --seconds 30

  지금까지 나온 실사용 값

      모델              입력   FPS    한 프레임   CPU     파일
      -------------------------------------------------------
      v2_best           320   26.3    38.0 ms   78 %   10.06 MB
      v2f_int8_640      640   21.1    47.4 ms   72 %    2.90 MB
      v2e120_fp32_640   640    7.7   129.2 ms   92 %   10.63 MB
      v2f_fp32_640      640    7.5   134   ms   89 %   10.14 MB

  같은 640 에서 INT8 이 FP32 보다 2.8배 빠르고 CPU 를 17%p 적게 씁니다.
  이 프로젝트에서 INT8 은 "전력을 아끼는 수단" 이 아니라
  "640 을 실시간으로 쓰게 해 주는 유일한 수단" 입니다.
  FP32 640 은 7.5 FPS 라 감시가 성립하지 않습니다.

  카메라 관련 : CAM_BUFFER 를 1 로 두면 프레임의 1/3을 버립니다(20 FPS).
  3 으로 바꿔서 30 FPS 가 나옵니다. 이미 3 으로 돼 있습니다.

 5. 아직 아무도 측정 안 한 것 — 나눠서 하면 좋겠습니다
────────────────────────────────────────────────────────────

  (1) 오검출 측정  ★ 제일 급합니다
      칼과 인형을 화면에서 완전히 치우고
          python3 detect_rate.py --wait 10 --save
      여기서 나오는 knife / outlet 검출률이 전부 오검출입니다.
      실제로 책을 knife 46%, 사람 어깨를 knife 71% 로 잡은 걸
      봤습니다. 71% 면 문턱값을 0.50 으로 올려도 안 걸러집니다.
      "칼을 잘 찾는가" 만 봤지 "헛것을 안 잡는가" 는 한 번도 안 쟀습니다.

  (2) 기울어진 칼
      45도, 수직, 거꾸로. 팀 보완사항이었는데 아직 못 쟀습니다.

  (3) outlet(콘센트)
      한 번도 촬영·측정하지 못했습니다.

  (4) 거리별 표
      0.5 / 1 / 1.5 / 2 m 에서의 검출률 → "유효 감시 거리" 확정
