# 파이프라인 트레이싱 사용법 (2026-09-16)

WARBOY 프로젝트에서 퓨리오사 SDK가 만들어 주던 타임라인 그림을, 라즈베리파이에서
직접 만들어 보는 도구다. 출력 형식(**Chrome Trace Format**)이 같으므로 같은 뷰어로 본다.

## 파일

| 파일 | 위치 | 설명 |
|---|---|---|
| `trace_util.py` | `examples/` | 트레이서 본체. 두 스크립트가 공용으로 쓴다 |
| `EX_13_traced.py` | `examples/04_Lightweighting/` | 분류 파이프라인(EX_13) 트레이싱판 |
| `EX_03_traced.py` | `examples/05_Object_Detection_Based_On-Device_AI/` | 검출 파이프라인(EX_03) 트레이싱판 |

원본 파일은 **건드리지 않았다.** 트레이싱판은 원본 로직을 그대로 두고 구간 측정만 넣은 사본이다.

## 타임라인 그림 보기

1. 보드의 `trace_*.json`을 MobaXterm 파일 탐색기로 **PC에 내려받는다**.
2. 크롬에서 <https://ui.perfetto.dev> 를 연다.
3. JSON 파일을 창에 **끌어다 놓는다**. (또는 `chrome://tracing` → Load)

보이는 것:

- **가로 막대** — 각 단계가 언제 시작해 얼마나 걸렸는지. `frame` 막대 안에 하위 단계가 겹쳐 그려진다.
- **막대 사이의 빈틈** — 아무 일도 안 하는 구간. `waitKey` 같은 대기가 여기 보인다.
- **CPU per-core %** — 코어별 사용률 그래프. 라즈베리파이 5는 코어가 4개다.
  한 코어만 100%이고 나머지가 낮으면 **병렬화 여지가 있다는 뜻**이다.
- **CPU total %** — 전체 평균.
- 막대를 클릭하면 아래에 정확한 시간이 뜬다. 구간을 드래그하면 그 범위 통계가 나온다.

## 측정할 때 지킬 것

- 다른 프로그램을 종료하고 돌린다. CPU를 나눠 쓰면 값이 틀어진다.
- 비교할 두 경우는 **연달아** 측정한다. 보드 온도가 달라지면 결과가 흔들린다.
- 04와 05를 비교할 때는 **반드시 손을 화면에 넣은 상태**로 한다.
  EX_13은 손이 없으면 추론을 건너뛰지만 EX_03은 항상 추론하므로, 손이 없으면 불공정한 비교가 된다.

## 무엇을 알아낼 수 있나

1. **04 실습에서 남은 42.3 ms의 내역.** 지금까지 "손 검출 20~25 ms, waitKey 10 ms" 는 추정이었다. 이 도구로 확정된다.
2. **`waitKey(10)`을 `waitKey(1)`로 바꿨을 때의 효과.** 바꾸기 전후로 두 번 떠서 비교한다.
3. **04(분류)와 05(검출)의 파이프라인 차이.** 손 검출이 빠지고 후처리가 늘어난 것이 그림으로 보인다.
4. **코어를 놀리고 있는지.** 4코어 중 하나만 쓰고 있다면 멀티프로세싱으로 개선할 여지가 있다는 근거가 된다.

## 퓨리오사 SDK와 다른 점

| | 퓨리오사 (WARBOY) | 여기 |
|---|---|---|
| 켜는 법 | `FURIOSA_PROFILER_OUTPUT_PATH` 환경변수 | 코드에 `with tr.span(...)` 삽입 |
| 만드는 주체 | SDK 런타임이 자동 | 직접 구간을 지정 |
| 볼 수 있는 것 | **NPU 내부 동작 포함** | CPU 쪽 단계와 코어 사용률까지 |
| 출력 형식 | Chrome Trace Format JSON | **같음** |
| 뷰어 | chrome://tracing, Perfetto | **같음** |

NPU가 없으므로 하드웨어 내부(연산기 가동률, DMA)는 볼 수 없다. 대신 파이프라인 단계는 똑같이 보인다.
